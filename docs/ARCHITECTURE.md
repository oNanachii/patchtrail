# 架构与关键取舍

PatchTrail把“模型提出动作”与“程序执行及判定结果”分开。首版控制公开输入范围，让有限任务中的状态、审批和验证可以被复现。

## 模块

| 模块 | 职责 |
| --- | --- |
| api.py | 请求校验、操作端权限、公开demo边界和错误响应 |
| service.py | Agent循环、预算、检查基线、补丁确认、恢复与终态 |
| providers.py | DeepSeek真实传输与明确标识的脚本provider |
| storage.py | SQLite状态、事件、幂等请求、乐观版本和重启恢复 |
| tasks.py与fixtures | 版本化任务、可编辑文件白名单和固定检查命令 |
| workspace.py | 有界读取、路径检查、内容哈希、补丁digest和新副本 |
| sandbox.py | Docker/Podman受限执行、输出与时间边界、容器清理 |
| web | 可替换的功能前端，通过公开REST契约操作 |

## 三项面试主线

**模型说完成不等于检查通过。** Agent只能保存提案，不能直接修改原仓库或把状态设为成功。确认之后重新建立验证工作区；测试文件不在可编辑集合中。基线必须是真正执行过用例的失败，避免把镜像缺失等基础设施错误错当成业务错误。

**确认绑定的是具体内容与现场。** 提案digest包含源码、旧新内容、diff和工作区指纹；确认还要匹配运行版本。现场漂移会被拒绝。确认和状态变化在SQLite事务中提交；同一确认的HTTP响应丢失后，重试不会重复触发验证。

**恢复需要重新核对状态。** diagnosing/verifying在进程重启后标为interrupted，awaiting_approval保留。恢复验证从固定源码和已确认提案重建，不依赖半完成的临时目录。模型请求结果未知时不自动再次请求，保留相关记录供操作者判断。

## 为什么先用这些边界

SQLite加单worker适合首版的单机容量与可解释性。并发竞争用数据库事务和版本检查处理，暂不引入分布式队列。预置任务让API、运行时和容器边界可先接受独立验收；扩展自带仓库前需要增加管理员任务注册、依赖镜像及更完整资源治理。

脚本provider与DeepSeek使用同一套工具和状态机。前者验证运行规则，后者才提供模型效果数据。公开演示的内置答案可从开源代码看到，不能作为未知修复能力测试。

容器提供具体隔离与资源约束，不意味着任意代码绝对安全；有限测试通过也不意味着程序对所有输入正确。正式多租户服务、任意仓库执行、自动合并PR和通用修复准确率不在v0.1范围内。
