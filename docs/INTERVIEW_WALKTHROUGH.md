# 面试讲解与本人验收

项目代码由AI辅助实现。面试时把系统已实现、本人做过的判断和本人能独立修改的部分分别说明；下面的检查点需要本人实际完成，文档生成不代表掌握。

## 三分钟讲述顺序

先解释用途：把一个带测试的Python修改任务组织成可检查的流程，记录模型看过什么、建议改什么，以及测试是否真的通过。当前操作者能在网页导入自己的源码和测试，预览后确认为私有快照；公开访问保留三个已知回归任务的脚本演示。

接着沿一条实际运行讲：选择已有任务或导入源码，单独确认真实调用费用，观察原测试失败，读一份源码，审查diff，确认准确补丁和运行版本，查看新工作区的容器输出。五个工具分别是读文件、搜索、固定检查、单文件提案和最多三文件补丁包。脚本演示只说明运行时行为；真实模型结果另有日志和报告。

用自己的话解释三个名词：不可变快照是本次任务固定的源码版本；digest是具体改动内容的指纹；version是运行记录的版本号。它们分别帮助核对“从哪份代码开始”“批准了哪份补丁”“是否还在同一运行状态”。导出的diff只是建议，可能尚未验证；系统只在验证副本中应用它，不自动修改原项目或合并PR。

最后讲一个真实错误或取舍，例如创建成功但HTTP响应丢失后的重复点击、审批前工作区变化、进程在模型请求期间中断。说明如何复现、代码怎样处理以及结果在哪看。

首轮真实DeepSeek验收已有一个实际案例：模型任务仍在运行，客户端查询却因SQLite锁竞争返回500。客户端没有再次创建任务，而是读取原run_id，确认已到待审查状态，再验证同一提案。这说明接口错误不能直接当作业务未提交。后续修正把存储忙映射为503、只对读取做有界重试，并在单Store实例内串行数据库操作；这些保证与跨进程协调的范围要讲清楚。

## 可以沿记录展开的实际案例

文本分类仓库的一个小功能任务是在`SampleStore.correct_label`源码快照上增加可选`expected_revision`。两个人同时打开版本0，A保存后升为版本1，B带着旧版本0再保存应被拒绝，且标签和历史保持不变。模型需保留旧调用方式并在事务内核对版本。该任务完成真实模型提案、内部审查、5条容器用例和导出后的独立复验；不表示模型补丁已自动合入第二项目主分支。

也要讲一个没有通过的例子：pytest摘要任务的第一份提案删除原有异常接口，并错误接受全跳过；反馈后的另一份提案仍改变既有unittest行为。两份均在审查后拒绝并取消，未应用。运行器本身的pytest支持另有实际OCI检查，模型任务没完成不等于系统不支持pytest。保留错误与拒绝，比只列成功数字更能说明审阅为什么必要。
